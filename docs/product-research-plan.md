# Product Research Plan

> 状态：准备完成，尚未执行真实参与者研究。本文不包含伪造的访谈、可用性结论或生产数据。

## 共同方法

### 招募条件

- 近 3 个月实际使用过至少一种编码 Agent。
- 能带一个可公开或可本地操作的小型仓库参加测试。
- 覆盖个人开发者、团队技术负责人和负责工具采购/推广的人。
- 不招募 AgentArena 当前主要贡献者作为首次可用性样本。

### 会话设置

- 每次 45–60 分钟，经同意后录屏或只记录观察表。
- 主持人不讲解界面，不告诉参与者“正确路径”。
- 使用参与者熟悉的本地环境；敏感仓库不离开设备。
- 先记录任务完成事实，再记录主观感受，避免用态度代替行为。

### 统一观察表

| 字段 | 记录方式 |
| --- | --- |
| 参与者编号与角色 | 匿名编号、角色、Agent 使用经验 |
| 首次点击 | 页面与控件，不记录仓库内容 |
| 关键路径 | 打开、选择、启动、完成、查看结果 |
| 停顿与回退 | 时间点、可见原因、是否自行恢复 |
| 错误 | 原文分类，不复制密钥、路径或提示内容 |
| 结果理解 | 能否说清成功、失败、成本状态和推荐依据 |
| 主观评价 | 会后 1–5 分与一句原因 |
| 主持人备注 | 事实与推断分开写 |

### 编码框架

- `discoverability`：找不到入口或下一步。
- `readiness`：安装、登录或兼容性阻塞。
- `task-fit`：不理解任务包与仓库关系。
- `trust`：不相信分数、成本、冠军或失败原因。
- `evidence`：找不到改动、检查或回放。
- `value-single`：单 Agent 基线价值。
- `value-multi`：多 Agent 选择价值。
- `commercial`：愿意为何种持续价值付费。

分析时先双人独立编码 20% 样本，再统一分歧。没有明显优势的非标准解释不得进入结论。

## R-1：主入口是否应为 Workbench

### 问题

新用户能否在不解释的情况下，从默认页完成一次可信评测？旧版是否仍有不可替代能力？

### 样本

5–7 名参与者；至少 3 名从未见过 AgentArena，至少 2 名经常使用本地编码 Agent。

### 非诱导任务

“你想判断一个本地编码 Agent 是否适合这个仓库。请使用这个工具完成一次评测，并告诉我你会不会相信结果。”

### 主持脚本

1. “请从当前页面开始，边做边说你认为下一步是什么。”
2. 遇到停顿只问：“你现在在找什么？”
3. 完成后问：“你认为这次是否成功？依据是什么？”
4. 再问：“如果结果可疑，你会去哪里找证据？”
5. 最后展示旧版入口，问：“这里是否有刚才缺失、且会阻止你使用的能力？”

### 预先决策规则

- 若至少 5/7 无主持帮助完成“启动 → 完成 → 查看结果”，且没有两人以上发现同一个旧版独占阻塞能力，继续以 Workbench 为默认入口。
- 若 3 人以上在同一主步骤阻塞，先修该步骤，不讨论删除旧版。
- 任何历史结果无法读取、旧深链接失效或证据丢失，都直接阻止旧版退出。

## R-2：单 Agent 与多 Agent 的首次价值

### 问题

首次用户更快理解“给一个 Agent 建立可重复基线”，还是“同时比较多个 Agent”？

### 样本

8–10 名参与者，按个人开发者与团队决策者分层。每人完成两种流程，顺序交叉，避免先做的流程天然占优。

### 任务 A：单 Agent

“你刚更新了常用 Agent 的模型或配置。请建立一个以后能重复比较的基线。”

### 任务 B：多 Agent

“团队准备在两个本地 Agent 中选一个。请用同一个仓库任务做出初步判断。”

### 观察重点

- 首次价值出现时间：参与者第一次明确说出“这对我有用”的时间点。
- 是否理解同仓库、同任务、同检查的重要性。
- 是否会把一次结果误认为长期结论。
- 单 Agent 历史与多 Agent 排名哪个更容易被正确解释。

### 预先决策规则

- 如果某条流程的独立完成率高至少 20 个百分点，且结果理解错误不更高，则把它作为默认新手叙事。
- 如果差异不足 20 个百分点，保留两条路径，但首页先表达共同价值：“可重复、可检查的真实仓库评测”。
- 不因为参与者说“喜欢比较”就默认多 Agent；必须同时满足行为完成和正确理解。

## R-3：Adapter 稳定顺序

### 问题

现有 Adapter 应按什么顺序投入稳定化工作？

### 数据来源

- 真实维护者在 Windows、macOS、Linux 上执行 doctor、登录探测和一个受控任务。
- 自愿开启的本地事件只提供入口、完成状态和完整性汇总，不收集仓库内容。
- 失败记录按环境、安装、登录、命令变化、解析、超时、结果缺失分类。

### 执行表

| Adapter | 系统 | 安装发现 | 登录检查 | 受控任务 | 结果完整性 | 失败分类 | 可恢复性 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 待执行 | 待填 | 待填 | 待填 | 待填 | 待填 | 待填 | 待填 |

### 排序公式

优先级 = 用户需求权重 × 失败频率 × 失败影响 × 可修复性。四项在查看结果前各按 1–5 分定义；不得因某个 Adapter 更流行就忽略不可验证的登录或输出问题。

### 预先决策规则

- supported Adapter 出现无法识别输出或静默缺数据时，优先级自动升到最高组。
- blocked Adapter 在登录或上游限制未解除前不投入体验优化。
- 只有当现有 supported 路径达到已定义的可靠门槛，才重新讨论新增 Adapter。

## R-4：商业化目标

### 问题

用户愿意为哪种持续结果付费，而不是为“多一个按钮”付费？

### 样本

8–12 次问题访谈：个人重度用户、5–50 人研发团队负责人、负责采购或合规的人各至少 3 名。当前没有参与者，故这里只交付脚本与判定规则。

### 访谈脚本

1. “最近一次你需要判断某个编码 Agent 是否值得推广，发生了什么？”
2. “你现在如何保存、比较和解释结果？最昂贵的部分是什么？”
3. “一次跑分之后，什么信息会改变部署、采购或模型选择？”
4. “哪些能力必须留在本地？哪些汇总可以进入团队系统？”
5. “如果这个问题持续解决，你会从哪个预算支付？谁批准？”
6. 只有在了解现状后，才展示团队历史、可靠性监控、共享报告三个概念，分别询问取舍。

### 不得诱导

- 不直接问“你愿意为 AgentArena 付多少钱”。
- 不把“觉得不错”编码为付费意愿。
- 不在未决定数据政策前承诺云同步、无限使用或企业合规。

### 预先决策规则

- 至少 5 名目标角色描述同一种高频、已有成本的工作，且至少 3 名能指出预算拥有者，才进入定价探索。
- 若主要价值是一次性比较，不建立订阅假设；优先考虑服务、报告或团队部署形式。
- 若本地数据边界是购买前提，任何商业方案必须先明确数据政策，再讨论功能包装。
- 本研究完成前，不更改价格、套餐、权限或数据上传政策。
